# ADB PoC 结果（2026-09-29）

设备：`192.168.10.100:5555`，`finch`，Android 14。

## 已确认

- `package` Binder service 存在：`android.content.pm.IPackageManager`。
- 从设备 `/system/framework/framework.jar` 的 `IPackageManager$Stub` DEX 读取到：
  - `TRANSACTION_setHomeActivity = 80`
  - `TRANSACTION_setApplicationEnabledSetting = 86`
  - `TRANSACTION_setComponentEnabledSetting = 83`
  - `TRANSACTION_setComponentEnabledSettings = 84`
- `setComponentEnabledSetting` 的参数顺序为：`ComponentName, newState, flags, userId, callingPackage`。
- 设备当前默认 Home 为 `com.dangbei1.tvlauncher/com.dangbei.launcher.ui.main.MainActivity`。
- 目标包存在：`com.ucnacdx2.mitvhomebridge`、`com.example.tvsettingslauncher`、`com.dangbei1.tvlauncher`、`com.xiaomi.mitv.upgrade`。
- 通过 `su` 执行 `pm` 的 root fallback 可以运行；现有旧 bridge 日志显示 `root launch exit=0`。

## Binder 试验结果

直接从 ADB shell 调用：

```text
service call package 83 ...
SecurityException: cannot change component state of ...
```

结论：transaction 编号和参数布局已由 ROM DEX 确认，但 shell UID 调用被权限拒绝。不能据此宣称普通应用或 bridge UID 已获得部分 root 权限；必须安装/启动新 bridge 后采集 `MiTVHomeBridge` 日志，分别验证 bridge UID、system UID 和 root fallback。

## TvService 临时 Root 试验结果

通过：

```text
service call TvService 4400 s16 s s16 /sdcard/Download/tvservice-poc.sh
```

脚本实际输出：

```text
uid=uid=0(root) gid=0(root) groups=0(root)
context=u:r:misysdiagnose:s0
build=OS3.0.115.0.UFFMATV
```

在该临时 root 脚本内直接执行 `/system/bin/service call package` 后，以下操作均返回成功：

- transaction 83：禁用并恢复 `FallbackHome`；
- transaction 83：禁用并恢复 `MainActivityUserMode`；
- transaction 86：禁用并恢复 `com.xiaomi.mitv.upgrade`；
- transaction 80：重新设置 Dangbei Home。

因此目标 ROM 的主执行路径确定为：`TvService 4400 -> misysdiagnose root script -> service call package`。
`pm`/`cmd` 在该 SELinux 域中不可直接使用，正式脚本必须使用绝对路径的 `service call`。

## 当前安全结论

- 不能把 bridge 进程直接调用 package Binder 作为主路径；普通 shell 已被拒绝。
- 正式逻辑应优先调用已验证的 TvService 临时 root 链路，并保留 `su` 回退。
- 任何禁用动作前后都要用 `dumpsys package` 记录状态。
- 当前设备已有第三方 Home，因此可以进入“选择并验证默认桌面后再禁用 MiTV Home”的护栏流程。

## 安装器网络隔离 PoC（未通过）

通过 TvService 4400 执行临时 root 脚本时，脚本仍处于 `u:r:misysdiagnose:s0` 域。虽然
`id` 显示 UID 0 和完整能力掩码，但以下网络控制接口均不可用：

- `iptables owner --uid-owner 10010`：无法打开内核 socket，返回 `Permission denied`；
- `cmd netpolicy`：Binder transaction 失败；
- `nft`：设备不可用。

因此当前不能加入 UID 级防火墙规则，也不能声称已阻断安装器上报。域名/IP 级阻断仍需找到
受该 SELinux 域允许的网络控制入口后再做候选 PoC；在此之前不修改安装器组件和正式网络策略。

随后测试了更窄的 `appops` 网络权限候选（`android:internet`），仍由 TvService 脚本
执行并在同一脚本中恢复。`cmd appops get/set` 全部返回 `Failed transaction (2147483646)`，
说明 `misysdiagnose` 不能通过该入口调整安装器 UID `10010` 的网络权限。当前已验证的
`iptables`、`nft`、`netpolicy` 和 `appops` 路径均不可用，因此不加入安装器网络隔离代码，
也不禁用安装核心组件。

## KernelSU Magica 与持久化研究状态

TvService 临时 root 已确认可执行 PackageManager Binder 操作，但这不等价于 KernelSU Magica
所需的内核模块加载、内核 escape 或长期 root 服务。当前检查未发现可访问的 `ksud`、
`kernelsu.ko` 或 `/sys/module/kernelsu`，`/data/adb`、`/proc/kallsyms` 和 `/dev/kmsg`
也受当前 SELinux 域限制。除非后续发现真实可执行的 KernelSU 入口，否则不实现 Magica
适配器。

TvService 持久化能力属于后置研究项，不属于当前一期交付范围。暂不尝试写入启动链、修改
分区挂载或部署持久化文件；当前交付只依赖一次性的 TvService 脚本生命周期。持久化 PoC
必须另行设计为只读/可恢复验证，并且不能阻塞 Bridge、Optimizer 和安装器分析工作。

## KernelSU/Magica 结论澄清

当前设备安装的是 Magisk（包名 `com.topjohnwu.magisk`，versionCode `30700`），未发现
KernelSU 管理器、`ksud`、`kernelsu.ko` 或 `/sys/module/kernelsu`。因此本轮 `ksud`
探测失败首先说明“设备没有 KernelSU 内核运行时”，不是证明 Magica 在所有 ROM 上都不可行。

已拉取并检查 KernelSU Magica 相关补丁。该实现的 `late-load` 依赖 KernelSU 内核侧代码
提供的 escape、凭据和 SELinux 初始化，再由 `ksud` 调用；补丁本身不是可独立运行的 root
二进制，也不能由 TvService 的一次性 UID 0 脚本替代内核接口。当前设备仅有 Magisk，且
`misysdiagnose` 域访问 `/data/adb`、`/proc/kallsyms`、`/dev/kmsg` 均受限，所以不能
仅通过下载 GitHub 源码完成有效 Magica 试验。

后续若要验证“可行”路线，前提是先为 finch 准备匹配其 kernel/KMI 的 KernelSU 内核模块
和可恢复测试启动链；在此之前，TvService 只能作为 PackageManager 操作的临时 root
backend，不能宣称可替代 KernelSU 或实现免解锁 BL root。
