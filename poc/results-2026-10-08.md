# TvService 域内能力实测（2026-10-08）

设备：`192.168.10.100:5555`，`finch`，Android 14，`OS3.0.115.0.UFFMATV`。

脚本经 `service call TvService 4400 s16 s s16 <脚本路径>` 执行，实际进程为 `uid=0` / `u:r:misysdiagnose:s0`。
脚本 stdout 不回传，所有输出走 `log -t MITVPROBE`，宿主用 `adb logcat -s MITVPROBE` 读取。

## 这个域里还有什么工具

- `/system/bin/settings`(35B)、`appops`(33B)、`am`(207B) 都只是 exec `cmd` 的包装脚本 → `rc=127`。
- 直接执行 `/system/bin/cmd`(140512B) → 服务侧拒绝 shell-command 通道，回 `Failed transaction (2147483646)`。
- `/system/bin/app_process`（→ `app_process64`，权限 755）执行被拒：`inaccessible or not found`，即 SELinux 拦截，不是文件缺失。
- 因此该域内实际可用的只有 `/system/bin/service call`（原生 Binder）与 `log`。进程是 uid 0，能力掩码完整，
  所以 `service call` 能过 ROOT_UID 豁免。

## 脚本在域内怎么执行、结论怎么回来（补测）

- TvService 不在原地执行传入的脚本：它先把脚本复制到 `/data/diagnosis/command.sh` 再执行。
  脚本里的 `$0` 因此是 `/data/diagnosis/command.sh`，**不是**调用方给的路径；脚本想定位一个
  App 也能读到的位置只能写死路径（实测 `V=${0%.sh}.result` 落到了 `/data/diagnosis/`）。
- 外层 `service call TvService 4400 …` 在脚本跑完之前就返回：实测外层耗时 194 ms，而脚本自身
  的日志时间戳跨了 314 ms。App 侧要拿脚本的结论，必须轮询而不是等外层返回。
- stdout 与退出码都不回传（`exit 7` 仍然只有 `Result: Parcel(00000000)`）。可用的回读通道是：
  脚本把结论写进 `/sdcard/Download/*.result`（域内可建、可覆盖别的 uid 建的文件且所有者不变），
  App 再读回。
- `service call` 的错误形态：事务号不存在 → `Result: Parcel(Error: 0xffffffffffffffb6 "Not a data
  message")`；服务名不存在 → `service: Service <name> does not exist`。这两种可识别，正好覆盖
  "transaction 号随 ROM 漂移"这个风险。但**参数不匹配**（`service call activity 83 i32 5`）与
  对不存在的包调用，都回干净的空 `Parcel`——回执正常不代表操作成功。

## 回读通道必须按调用隔离（bridge 0.3.5 实测）

上面那条回读通道有个前提：**每次调用用自己的一对文件**。bridge 0.3.4 之前用固定文件名
（`mitv-home-bridge.sh` / `.result`），而它有两个线程在并发驱动 TvService——Home 切换一个、
安装器限制一个——两边都在 `finally` 里删这两个文件。

在 finch 上以"应用无 su"状态实测抓到了这个竞态（线程号 27049 是安装器，27048 是 Home 切换）：

```
.545  27049  verdict="OK       WRITE_SETTINGS (deny):"   <- 安装器的 appop
.721  27048  verdict=""                                   <- Home 线程的组件操作
.950  27049  verdict="OK Result: Parcel( … )"             <- 安装器的 force-stop
```

修复前的同一段日志里，`.763 27048` 读到的是和 `27049` 一模一样的 appops 结论（越界读到了别人的
文件），而 `27049` 的 force-stop 读到空串——Home 线程的 `finally` 把它的结论删了，于是已经生效的
force-stop 被报成 `forceStop=false`。同一竞态也允许一个线程的脚本在域复制之前被另一个线程覆盖，
使调用方指定的脚本根本没跑。

所以：**结论文件名（以及脚本名）必须带每次调用的唯一序号**，不能是共享常量。

## 安装器限制四条命令

| 命令 | 域内能否用原生调用走通 |
| --- | --- |
| `appops set com.android.packageinstaller WRITE_SETTINGS deny` | **可以** |
| `am force-stop com.android.packageinstaller` | **可以** |
| `settings delete system pi_config` / `settings put system pi_config …` | 不行 |

### appops

等价调用：`service call appops 31 i32 23 i32 10010 s16 com.android.packageinstaller i32 <mode>`
（`TRANSACTION_setMode=31`、`OP_WRITE_SETTINGS=23`、安装器 uid `10010`）。

实测：改成 `allow`(mode 0) → 宿主 `cmd appops get` 回读 `WRITE_SETTINGS: allow`；
改回 `deny`(mode 2) → 回读 `deny`，与原始状态一致。

`cmd appops set … deny` 对应 mode **2**（`MODE_ERRORED`）。

### force-stop

等价调用：`service call activity 83 s16 <包名> i32 0`（`TRANSACTION_forceStopPackage=83`）。

实测目标 `com.xiaomi.aitranslate`：返回空 Parcel（无 SecurityException、无 `Failed transaction`），
宿主侧 `pidof` 从 `4181` 变为空，进程确被杀。

## settings provider 为什么走不通

- `service call settings <code> …` → `service: Service settings does not exist`。
  同时 `service check settings` 报 `found`，`dumpsys settings` 也能正常 dump 出内容（域内同样可以）。
- 从 Java 侧 `ServiceManager.getService("settings")` 能拿到 `BinderProxy`，
  但 `getInterfaceDescriptor()` 为空字符串；同一探针里 `lock_settings` / `appops` / `activity`
  分别正常返回 `com.android.internal.widget.ILockSettings` / `com.android.internal.app.IAppOpsService` /
  `android.app.IActivityManager`。
- 描述符为空意味着 AIDL transaction 号无从得知；`service call` 又根本取不到这个服务；
  该域内 `app_process` 被 SELinux 拒绝，无法自建 Java 客户端手拼 Parcel。
  结果是这一步在域内没有可用路径。

## 对 v0.3.2 发布说明的更正

v0.3.2 发布说明与当时的 README 写的是"四条命令全部失败……确认不存在第二条路"。
按上面的实测，四条里有两条（appops、force-stop）可以用 `service call` 直接做到；
只有 settings provider 那一步没有第二条链路。模块与 bridge 仍按原样用 root 执行，
不硬编码 transaction 号（会随 ROM 漂移）。

## pi_config 能否绕开 provider、直接改文件

`pi_config` 存在 `/data/system/users/0/settings_system.xml`（system 命名空间；
`dumpsys settings` 里为 `_id:305 name:pi_config pkg:root`，说明是运行时由 uid 0
经 provider 写入的值）。本机是 Android 14 的 ABX 存储：文件头是 `ABX` 二进制 XML，
没有 SQLite 兜底（`/data/data/com.android.providers.settings/databases/` 不存在）。

**权限层面可行**：在 TvService 域（uid 0 / misysdiagnose）里，
`/data/system/users/0/` 可以创建文件（新建文件自动获得 `u:object_r:system_data_file:s0`），
`settings_system.xml` 本身 `touch` 返回 `rc=0`（size 不变、mtime 变化），随后清理干净。

**但这条路不成立**，因为：

1. 值不在文件里生效，而在 provider 的内存里。`dumpsys activity providers` 显示
   `com.android.providers.settings/.SettingsProvider` 的 `process=system`、
   `proc=ProcessRecord{36b2027 537:system/1000}`、`singleton=true` —— 它不单独成进程。
   系统里任何一次设置变更都会整份重写该 XML（观测到 mtime 在 18:53 自行变化）。
   外部改/删会在下一次写入时被覆盖，要让它重新读盘只能重启那个进程，即重启电视。
2. 删主文件不等于"没有这个设置"：同目录存在 `settings_system.xml.fallback`
   （12411 B，18:17 的快照），provider 的兜底逻辑会从它恢复，拿到的是旧值。
   而且删整份文件会让整个 system 命名空间（音量、声音输出、`mitv.service` 上百条）
   回默认，不可逆。
3. 语义也不对：删掉 `pi_config` ≠ 解除安装拦截，厂商缺省大概率仍是开启拦截。
   模块的做法是 `settings delete` 之后 `settings put` 一个
   `{"pi_intercept_switch":false,"app_pi_control":false}`，只删不写回可能反而回到拦截开启。

**结论（"编辑文件 + 重启"）**：重启之后 provider 会重新读盘，所以"改文件 + 重启"在原理上
能生效——上一段说的"改文件不生效"，指的是**改完不等重启**那一段窗口。但这条仍然不做：
该文件是 ABX 二进制 XML，文本编辑改不动，必须先解码再重新编码；`.fallback` 快照与"删整份
文件等于丢掉整个 system 命名空间"的问题照旧；而"重启"这一步在域内虽然够得着（power 服务在
ROOT_UID 豁免下可用），却没法实测——验证成功的代价就是电视重启一次，不值得。

要"不靠 su 也能改 pi_config"，可行方向不是改文件，而是让 bridge 自己写：
`WRITE_SETTINGS` 在 Android 上表现为 app-op，而上面已实测该域可以改 app-op
（`service call appops 31 …`），所以模块或 TvService 链路先给 bridge 打开
`WRITE_SETTINGS`，bridge 再用普通 `Settings.System.putString` 写入。
这条没有端到端验证（需要改 APK 并装机）。

## 这三步在 adb shell 里全都能做（2026-10-08 补测）

上面几节反复说"这个域里只有 `service call` 可用"，容易被读成"这些操作没有别的通道"。
真正区分的是**调用方**，不是设备上有没有命令。以 `uid=2000(shell)` / `context=u:r:shell:s0`
的普通 adb shell 实测（`id` 确认不是 root，`ps` 显示 `adbd` 也跑在 shell 下）：

| 操作 | adb shell (uid 2000) | TvService 域 (uid 0) | bridge 应用 (uid 10075) |
| --- | --- | --- | --- |
| 改安装器 `WRITE_SETTINGS` appop | **可以**（改成 `allow` 回读 `allow`，改回 `deny` 一致） | 可以（`service call appops 31`） | 不行，exec 不到 `cmd` |
| `am force-stop <包名>` | **可以**（`pidof` 从 `30591` 变为空） | 可以（`service call activity 83`） | 不行 |
| `settings put system pi_config …` | **可以**（附加的 `probe` 键能在回读里看到） | 不行，取不到 settings Binder | 不行 |

所以 TvService 域解决的是"应用没有 root"，不是"设备上没有可用的命令通道"。bridge 借它是因为
自己只是普通应用；用户手上有 adb shell 时，这三步一步都不需要 root。对没有 root 的用户来说，
安装器限制能不能解除取决于这一步有没有人做，而不是取决于有没有 root。

验证方式都不是看返回码（`cmd appops set` 即使无效也不报错），而是写入后回读实际值。
`pi_config` 那条用了附加键 `probe`，因为当前值与目标值相同，直接回读证明不了写入生效。
